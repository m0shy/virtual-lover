# 部署详解

写给想了解原理、手动部署或排查问题的读者；只想快速用起来的话，看根目录 README 的 `setup.bat` 流程即可。本文是我按真实运行和维护时的架构整理的，先交代几个贯穿全部文档的说法：

- **v1 / v2**：本项目两代架构。v1 是旧编排——以 AstrBot 容器为大脑、Milvus 三容器为记忆库（AstrBot 是被替代的开源机器人框架；Milvus 是向量数据库）；v2 是现行的「1 容器 + 1 进程」架构，也是本文的主角。
- **vl**：本项目及其宿主机主进程的代称（virtuallover 的缩写）。
- **NapCat / 协议端**：QQ 协议端指实际登录 QQ 号、收发消息的组件，本项目的协议端是 NapCat 官方镜像跑成的容器（NapCat 是第三方实现的 QQ 协议端，非开源许可、禁商用），对话内容经 OneBot v11 开放规范（QQ 机器人消息的开放标准）与系统其余部分互通。compose 里它的服务名叫 `heart`，容器名叫 `vl-heart`。
- **O / R 编号**：文中出现的 O10、O11、R7 等是本项目的内部任务编号与修缮轮次编号（定义见 PERF_SPEC），保留只为与 SPEC、provenance 对得上号。

## 架构与数据流

**v2 现行架构（1 容器 + 1 进程）**：她的全部能力都跑在宿主机 `virtuallover` 单进程里（OneBot 反向 WS 服务端、人格装配、LLM、内嵌向量记忆、情绪/日记/主动消息、管理控制台——「反向 WS」指由协议端容器主动向本机服务发起的 WebSocket 长连接），编排里常驻的容器只有 napcat 一个器官；旧五容器编排整体保留在 compose 的 `legacy` profile 仅供 14 天回退窗口使用（回退 SOP 见 [docs/回退.md](回退.md)）。

```
部署者QQ(常用号) ⇄ 腾讯QQ服务器
                      ⇅ (非官方协议 OneBot v11)
                 [napcat 容器] --反向WS ws://host.docker.internal:6199/ws--> [宿主机 virtuallover 进程]
                                                              ├── LLM API（豆包/DeepSeek/任意 OpenAI 兼容）
                                                              ├── 内嵌向量库 local/vl_data/（numpy 余弦检索，无需容器）
                                                              ├── 管理控制台 127.0.0.1:8787（随进程内嵌）
                                                              └── 宿主机 GPT-SoVITS 语音(可选) 127.0.0.1:5000
```

**legacy 回退栈（v1 编排，默认停机）**：

```
                 [napcat 容器] --反向WS--> [astrbot 容器]（仅 docker compose --profile legacy up -d 时）
                                              ├── [milvus 容器群] 记忆（旧库实测为空，docs/回退.md §0）
                                              ├── [milvus-etcd / milvus-minio] Milvus 的元数据与对象存储
                                              └── 语音 host.docker.internal:5000
```

## 服务与端口（最小暴露模型）

| 容器 | 镜像 | 宿主机可访问 | 用途 |
|---|---|---|---|
| astrbot | soulter/astrbot（已钉 v4.28.2，legacy 组默认停机） | ✅ 127.0.0.1:6185（面板，仅回退时用） | v1 大脑（回退窗口内） |
| napcat | mlikiowa/napcat-docker | ✅ 127.0.0.1:61990 | QQ 协议端（WebUI 由控制台代管） |
| milvus-standalone | milvusdb/milvus:v2.6.2（legacy 组默认停机） | ❌ 仅容器网络 | v1 向量数据库（旧库空，O10 停机） |
| milvus-etcd | quay.io/coreos/etcd:v3.5.18（legacy 组默认停机） | ❌ 仅容器网络 | Milvus 元数据（注意镜像在 quay.io，手动 pull 需带前缀） |
| milvus-minio | minio（legacy 组默认停机） | ❌ 仅容器网络 | Milvus 对象存储 |

宿主机进程（非容器）：**virtuallover 单进程** —— `python -m virtuallover`（`.venv` 虚拟环境隔离；由 setup.bat 创建，全部一键 bat 与 `scripts/service.py` 都优先解析仓库根 `.venv\Scripts\python.exe`、缺失时回退 PATH 里的 python），她的大脑与**管理控制台**（`virtuallover.console`，随进程内嵌）都在这个进程里。控制台只绑 `127.0.0.1:8787`，登录后可以填 API Key、改人格、QQ 扫码、启停/重启/备份；控制台随 vl 同起同停，`local/console.json` 里的 pid 就是 vl 主进程 PID（`一键停止.bat` 据此兜底精准结束进程）。61990 端口发布到本机（compose 用的是中性端口映射 127.0.0.1:61990→容器 6099；R7 之前 6099 是上游文档的默认端口，换成非默认端口后端口表不再暴露上游名），供控制台代理 WebUI 扫码用，vl.toml 的 `[console].nc_base` 可配。

可选的两个宿主机伴生进程（都不装也能用）：

- **本地大脑 llama-server(8002)**：llama.cpp 提供本地推理（任意 GGUF 大语言模型均可；本部署测试用 Qwen2.5-7B），仅绑 `127.0.0.1:8002`；由管理控制台「引擎与人格」页的「切到本地大脑」（`scripts/brain_switch.py local`）拉起并写入 vl.toml，`一键启动.bat` 检测到配置指向本地时会自动带起，看护进程 30 秒探活、判死重拉、熔断冷却（细节见下文「开机自启」）。配置不指本地时不启动、不探测。
- **GSVI（GPT-SoVITS-Inference）语音引擎(5000)**：`tts.auto_start=true` 时由 vl 进程在首次开口时自动拉起（上游固定监听 `0.0.0.0:5000` 且无鉴权，暴露面分析见 [语音指南](语音.md) 第 5 节）。

整程序启停统一走 `一键启动.bat` / `一键停止.bat` / `一键状态.bat`（即 `scripts/service.py start|stop|status`）：按序编排 napcat 容器 → 本地大脑(如配置) → vl 主进程 + 独立看护；停止时 vl、本地大脑、GSVI、napcat 全停。

**网络暴露模型**：默认所有宿主机端口只绑定 `127.0.0.1`（本机浏览器可用，局域网不可达）；6199（OneBot 反向 WS）、19530/9091（Milvus）、9000/9001（MinIO）**完全不发布**——它们只服务容器网络内部互通，发布出去没有任何收益，只有风险（MinIO 默认口令、Milvus 无认证、6099 可接管 QQ 会话）。需要从手机等其他设备访问面板时，把 compose 里对应端口的 `127.0.0.1:` 前缀去掉，**并同时修改面板默认密码**；在公共 Wi-Fi / 宿舍网环境请保持默认。

## 设计要点（为什么这样组织）

- **五容器同网络**：astrbot 按容器名 `milvus-standalone` 直连记忆库，napcat 按容器名 `astrbot` 反向连接，不需要任何手工网络操作。
- **启动顺序与自愈**：astrbot `depends_on: milvus(healthy)` 保证记忆插件一起动就能连上；全部服务 `restart: unless-stopped`，主机重启后整套自动回来。
- **端口最小暴露**：见上节「网络暴露模型」——默认仅本机、内部端口不发布。
- **日志轮转**：所有容器 json-file 日志上限 10MB×3 份，长期运行不会撑爆磁盘。
- **napcat 挂载 `local/napcat_config`**：NapCat 官方镜像把框架配置放在匿名卷里，容器一删除就丢；显式挂载后 `docker compose down` 也不怕。
- **napcat 不再挂载插件目录（O11）**：v2 的表情包/媒体由宿主机进程以 base64 经 WS 直发；legacy astrbot 回退时自研插件不随行（v2 已内建等价能力，见 provenance）。
- **插件运行数据也在 local/**：`local/shared_plugin_data` 是全部插件的可迁移状态——「备份 local/ = 备份一切」成立。
- **插件依赖装在容器层**：容器重建后 AstrBot 会自动重装（首启最长约 10 分钟），属正常现象。
- **镜像源可切换**：默认官方源；国内网络在 `.env` 取消注释 5 行 daocloud 配置即可整体切换（见 `.env.example`）。
- **管理控制台（virtuallover.console）**：随 vl 进程内嵌，会话认证 + CSRF 防护（跨站请求伪造防御：写操作要求特定请求头）+ 写端点白名单；仅绑 127.0.0.1，不挂 docker.sock（容器编排动作走固定 argv 白名单，不给容器控制宿主 Docker 的能力）——入口能力与安全边界不冲突。

## 升级 SOP（重要：先备份再升级）

v2 的升级对象是**宿主机 vl 代码**（napcat 镜像 latest 由 compose 顺带检查）——`scripts/update.bat` 一键五步，每一步都与脚本实测流程一致：

```bash
scripts\update.bat
```

1. **升级前备份**（保命步骤，不可跳过）：交互确认后自动跑 `scripts\backup.bat`；选 N 直接取消更新
2. **拉取代码**：`git pull --ff-only`（本地有未提交改动或网络问题会失败退出，按提示 `git stash` 后重跑）
3. **刷新依赖**：`.venv` 里重装 `requirements.txt` + `requirements-dev.txt`（幂等，装过即快；失败只告警不中断——老依赖通常兼容）
4. **重启 vl 主进程**：`一键停止.bat` → `一键启动.bat`（napcat 容器保持在线不动；重启期间 QQ 消息会丢，属预期）
5. **验证**：轮询 `/api/status`（200/401 均为在线），2 分钟未就绪判定更新翻车，自动打印回滚指引

**回滚三步**（脚本尾也会打印同款指引）：

1. 回滚代码：`git log --oneline -5` 找更新前提交号，`git checkout <提交号> -- .`（或 `git reset --hard <提交号>`，先确认无未提交的本地改动）
2. 重跑 `scripts\update.bat`（再次重启 vl 生效）
3. 仍不行：用 `backup\` 里最近一次备份覆盖 `local\` 对应子目录（见下文「从备份恢复」）后重启

> **legacy 附注（旧栈回退窗口内才相关）**：`astrbot` 镜像钉死 v4.28.2（防跨版本行为漂移——v4.25 前后面板密码机制完全不同），钉死版本下 `docker compose pull` 是空操作，**升级 = 改版本号**：`.env` 里设 `ASTRBOT_IMAGE=docker.io/soulter/astrbot:<新版本号>` 后 `docker compose --profile legacy up -d`，`一键状态.bat` 验证（面板/记忆/QQ 三看）；回滚即把版本号改回去再 up。日常升级不走这条路。（本机镜像现状以 [docs/回退.md](回退.md) 文首的 R6 退役声明为准。）

## Linux / macOS 用户

编排本身跨平台，只有安装向导脚本是 Windows 专属：

```bash
docker compose up -d          # 启动 napcat
# 建 .venv 并装依赖：python3.11+ -m venv .venv && .venv/bin/pip install -r requirements.txt
# 运行 vl：python -m virtuallover（.venv 隔离；控制台随进程内嵌）
# 打开 http://127.0.0.1:8787 控制台完成扫码与配置
```

差异点：① 一键脚本请自行执行等价的 compose 命令；② 语音后端地址就写 `http://127.0.0.1:5000`——v2 的 vl 与 GSVI 同在宿主机，本机直连即可，**没有** Windows Docker Desktop 的 `host.docker.internal` 域名问题（该写法只属于 legacy 回退栈：astrbot 容器访问宿主机语音才需要它，原生 Linux 下需给 compose 加 `extra_hosts: ["host.docker.internal:host-gateway"]` 或改宿主机内网 IP）；③ 提交前密钥钩子需 `pwsh`（无则自动跳过）。

## 常用运维命令

日常只需要面对 napcat 一个常驻容器（vl 全家启停走一键 bat，见上文；**vl 代码升级走 `scripts\update.bat`，不是 compose pull**）：

```bash
一键启动.bat / 一键停止.bat / 一键状态.bat    # 日常启停与体检（napcat+本地大脑+vl+语音全家）
docker compose up -d            # 只起 napcat 常驻组（legacy 组不随行）
docker compose stop             # 停止容器（数据保留）
docker compose down             # 删除容器（local/ 数据与配置仍保留；可随时 up 回来）
docker compose pull heart       # 仅 napcat 跟随 latest，pull 才有意义（astrbot 已钉版本）
docker compose logs -f heart    # 看 napcat 日志
docker exec -it vl-heart bash      # 进 napcat 容器排查
```

### legacy 回退窗口专用（日常勿用）

```bash
docker compose --profile legacy up -d      # 起旧栈整组（astrbot + milvus 三件套，见 docs/回退.md）
docker compose --profile legacy ps         # 看旧栈容器健康
docker compose logs -f astrbot             # 看 astrbot 日志（仅回退模式）
docker exec -it astrbot bash               # 进 astrbot 容器（仅回退模式）
```

## 开机自启（Windows 计划任务，可选）

注册（当前用户登录 ONLOGON 触发，无需管理员；`<你的仓库目录>` 换成实际仓库根）：

```bat
:: 注册：登录即调 service.py start 拉起全家（napcat + 本地大脑(如配置) + vl + 看护）
schtasks /Create /F /TN "VirtualLover自启" /SC ONLOGON /TR "cmd /c cd /d <你的仓库目录> && .venv\Scripts\python.exe scripts\service.py start >> local\vl_data\logs\autostart.log 2>&1"

:: 撤销
schtasks /Delete /F /TN "VirtualLover自启"
```

- 未建 `.venv` 时把命令里的 `.venv\Scripts\python.exe` 换成机器上的 `python.exe` 全路径；仓库路径含空格时内部路径用 `\"` 转义；
- 登录后短暂弹出控制台窗口，`start` 跑完自动关闭；Docker 未就绪时 napcat 启动自动重试（`scripts/service.py` 的 `napcat_up`：3 次 × 间隔 30s）；
- 看护体系（`service.py` 的 `_daemon`）：vl 每 10s 巡检拉起；本地大脑(8002) 30s 探测、连续 2 次失败判死重拉、10 分钟内 3 次死亡熔断、5 分钟冷却后半开重试；重启退避按「最近死亡时刻」窗口——连续存活满 5 分钟计数重置。杀进程前一律按 pid + 命令行核验（防 pid 复用误杀）。

## 从备份恢复

1. 停止：`一键停止.bat`（vl/本地大脑/语音/napcat 全停，防恢复时被进程占用）
2. 用备份目录覆盖 `local/` 对应子目录（如 `backup\20260101_120000\vl_data` → `local\vl_data`）
3. 启动：`一键启动.bat`

## 贡献者注意

提交前请启用密钥自查钩子（一次性）：
```bash
git config core.hooksPath .githooks
```
之后每次 `git commit` 会自动扫描已跟踪文件中的密钥/令牌（规则见 `scripts/check-secrets.ps1`，个人专属规则放 `local/secret-patterns.txt`）。

## 卸载

`docker compose down` 后删除整个目录即可；Docker 镜像可用 `docker rmi` 按需清理。
